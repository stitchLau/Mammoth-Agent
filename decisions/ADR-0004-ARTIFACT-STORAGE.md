# ADR-0004: Artifact Storage（原始资料存储）

- 状态：Proposed（2026-11-12，等待负责人批准）
- 日期：2026-11-12
- 决策人：（待填）
- 相关需求/功能：M1 项目知识底座（资料导入、知识来源引用）

## 背景与约束

- Artifact 是**原始输入、不可被派生结果覆盖**（`docs/03-DOMAIN-MODEL.md`、`docs/06-KNOWLEDGE-AND-RAG.md`）。
- M1 本地/单机优先；数据根目录遵循 ADR-0002（可配置、禁止安装目录/`~/.dsh`/源码目录）。
- 元数据在关系库（ADR-0003 SQLite/Flyway）；本 ADR 只定**字节存储**。
- 安全：不得把客户资料写入代码仓库；备份/恢复必须可演练。

## 需要解决的问题

原始资料字节存哪里、如何去重/校验/备份/防误删，以及未来如何迁移到共享/服务端存储。

## 备选方案

- 方案 A：本地内容寻址目录 + 关系库元数据（建议）。
- 方案 B：SQLite BLOB（字节入库）。
- 方案 C：对象存储（S3/MinIO），适合服务端阶段，本轮未实现。

## 决策

采纳 **方案 A**：

1. 字节存储：`<数据根>/artifacts/<sha256[0:2]>/<sha256[2:4]>/<sha256>`（内容寻址，去重）。
2. 元数据存关系库：`artifact(id, project_id, sha256 UNIQUE, original_name, mime, size, source_note, uploaded_by, created_at)`；通过 `sha256` 关联字节。
3. 写入协议：同 sha 已存在 → 去重复用；否则写临时文件 → `ATOMIC_MOVE` → 置 **只读**。
4. 读取时校验 sha256；失败视为存储损坏并告警，不得静默返回。
5. 删除/清理仅经授权流程（先清只读属性再删），并写审计。
6. 抽象 `ArtifactStore` 接口（`put/get/exists/verify/delete`），M1 用本地实现；服务端阶段可替换对象存储（key = sha256）。

## 决策理由

- 实测（`docs/spikes/S5-ARTIFACT-STORAGE-SPIKE.md`）：文件系统写入 37 ms、读取 19 ms、备份 6 ms/5.35 MB；SQLite BLOB 对应 296 ms、43 ms、22 ms，且字节与 DB 备份耦合、无文件级只读保护。
- 只读属性 + 哈希校验提供两层不可变保障；备份就是目录复制，运维简单。
- 内容寻址天然去重，且路径短，规避 Windows 长路径问题。
- 与 ADR-0003 解耦：DB 只存元数据，备份体积与资料体积解耦。

## 取舍和影响

- 需要自建文件写入/校验/清理逻辑（`ArtifactStore`），并处理并发写、超长路径、杀毒扫描。
- 备份需同时覆盖数据目录与 SQLite 库，并用 sha256 校验一致性。
- 对象存储未验证；服务端阶段替换时接口不变。
- 大文件（> GB）本轮未测，M1 需补流式实现。

## 安全/数据/迁移影响

- 资料不进代码库、不进 DSH Home、不进 RAG 样例集；数据根目录权限由操作系统控制。
- 去重意味着不同项目可共享同一字节文件；**元数据按项目授权**，共享字节不等于共享可见性（M1 T10 验证）。
- 未来迁移对象存储：按 sha256 全量搬运 + 校验，元数据不变。

## 验证计划和结果

已执行（2026-11-12）：6 文件（4 唯一内容，含 5 MB 与 0 字节）双方案写入/读取/去重/只读/备份/删除恢复；文件系统方案删除被只读属性阻止、恢复成功。证据：`docs/spikes/S5-ARTIFACT-STORAGE-SPIKE.md`。

待补充：并发写、GB 级流式、备份一致性脚本、ObjectStore 实现（服务端阶段）。

## 回滚或替代路径

- 若文件系统方案在客户环境受限（如只读盘、策略禁止）→ 切换 SQLite BLOB（方案 B）：`ArtifactStore` 接口不变，M1 数据量可控。
- 服务端阶段 → 方案 C（对象存储），接口不变。
