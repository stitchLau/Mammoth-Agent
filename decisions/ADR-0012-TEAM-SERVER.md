# ADR-0012: 团队服务端部署与数据库演进（PostgreSQL 多实例归入 M5）

- 状态：**Proposed（M4 S6 按负责人决定仅文档化延期；团队服务器/TLS/PG 多实例未实施）**
- 日期：2026-11-13
- 决策人：项目负责人（方向确认）；Lead Agent 起草
- 相关需求/功能：M4 多用户共享、组织管理、团队服务端预案；M5 PostgreSQL/多实例
- 相关文档：`decisions/ADR-0003`（SQLite/PG）、`decisions/ADR-0008`（单机单写者/导出导入）、`decisions/ADR-0006`（会话/授权）、`docs/08-SECURITY-AND-TRUST.md`、`docs/dev-setup.md`

## 背景与约束

- 现状（2026-11-13 核对）：SQLite(WAL) + Flyway，单一 `DataSourceConfig`；`mammoth.data-root` 实例锁保证单写者；会话在 `session` 表（服务端不透明令牌）；登录限速 `LoginRateLimiter` 是**进程内内存**；Cookie 的 `Secure` 只在 `request.isSecure()` 时设置；无 TLS、无 `forward-headers` 配置、无 PostgreSQL 迁移目录。
- 负责人 2026-11-13 决定：M4 按单节点 + 反向代理 TLS + SQLite；**服务器与证书暂不处理**（内网/本机开发环境）；需要明确 PostgreSQL 多实例延后到哪个阶段。
- ADR-0008 定案：单机本地单写者；数据根必须本地固定盘；跨机用导出/导入；MCP 只读。团队服务端不能破坏该边界，除非另立 ADR。

## 需要解决的问题

1. 何时引入 TLS、Secure Cookie、反向代理信任；
2. 是否/何时引入 PostgreSQL 与多实例；
3. 多实例下的会话、限速、任务领取、备份恢复；
4. M4 的“多用户共享”如何在不引入 PG 的前提下成立；
5. 服务器与证书暂不处理时，M4 的最小交付是什么；
6. 与 ADR-0003/0008 的关系与更新方式。

## 备选方案

- **方案 A（推荐）**：M4 保持**单节点、单写者、SQLite**；多用户共享 = 一个服务进程内多用户 + DB 会话；如部署到内网团队，由反向代理终止 TLS，应用只信任代理头；PostgreSQL/多实例放 **M5**。
- **方案 B**：M4 就切 PostgreSQL + 多实例。能支持 HA/横向扩展，但需要 PG 迁移脚本、方言测试、任务锁、共享限速、备份恢复、TLS、部署运维；与当前交付节奏和“服务器/证书暂不处理”的决定冲突，M4 不采用。
- **方案 C**：保持纯本机，不做多用户共享。与 M4 的范围冲突，且现有 DB 会话/项目成员本已支持多用户，放弃可惜。

## 决策

采纳 **方案 A**，并明确以下 10 条：

1. **M4 默认形态**：仍然单节点、单写者、SQLite(WAL)；数据根规则、实例锁、导出/导入、MCP 只读均不变（ADR-0008）。
2. **多用户共享**：M4 的“多用户”是同一服务进程内的多个本地账号 + 项目成员 + DB 会话；不承诺多实例、跨机实时协作或共享网络盘数据根。
3. **TLS 预案**：若 M4 之后部署到内网/团队，必须由反向代理（Caddy/Nginx 等）终止 TLS；应用侧开启 `server.forward-headers-strategy=framework` 并只信任明确配置的代理；Cookie 使用 `Secure`、`HttpOnly`、`SameSite=Lax`；默认绑定 `127.0.0.1`，局域网绑定需显式配置并配合防火墙。
4. **服务器/证书暂不处理**：M4 不交付生产证书、域名、OS 服务化或公网暴露；S6 作为**团队服务器预案**（配置项、反向代理样例、验收清单），是否实施由负责人后续决定。
5. **PostgreSQL 多实例 = M5**，不是 M4/M4.5。M4.5 只做生产集成与运营启用（Jira 只读 API、CSM 适配、通知渠道启用、远程 Agent 网关可选），仍为单节点 SQLite。M5 的完整切片、迁移/切换、备份/回滚与验收见 `docs/specs/M5-PHASE5-PLAN.md`。
6. **M5 触发条件**（满足任一即评估）：需要 2 个以上应用实例/HA；单节点写入成为瓶颈；数据量/备份窗口超出 SQLite 可接受范围；需要跨机共享同一权威库；需要独立报表/只读副本。
7. **M5 前置**：更新 ADR-0003；提供 `db/migration-pg` 与 SQLite/PG 双跑迁移测试；JPA 方言/Hibernate 映射校验；任务领取改为 `SELECT ... FOR UPDATE SKIP LOCKED`（或等效）；登录限速/会话共享存储；`pg_dump/pg_restore` 备份恢复演练；TLS/部署/监控/回滚手册。
8. **共享会话**：当前 `session` 表已可被同一 DB 的多个进程读取；M4 不引入 Redis。多实例时，会话天然共享，但登录限速仍是进程内状态，必须替换为 DB/共享存储（M5）。
9. **备份/恢复**：M4 继续使用 ADR-0008 的 `VACUUM INTO` + Artifact 复制 + 校验；新增权威表必须加入 `AdminTables` 与演练；运营表（通知/任务/审计导入游标）默认不进导出。
10. **不破坏单写者**：M4 不引入第二个写 SQLite 的进程；后台任务 worker 只在 writer 进程内运行，且 MCP 只读进程不运行任务（`read-only=true` 条件）。

## 决策理由

- 现有代码与数据模型已经支持单进程多用户；M4 的用户价值（组织/权限、通知、外部 Agent、只读导入）不依赖 PG/多实例。
- 引入 PG/多实例会同时触发迁移、方言、任务锁、限速、备份、部署与运维问题，属于平台级变更；在“服务器与证书暂不处理”的前提下没有验证环境，强行做会制造未验证的生产风险。
- 反向代理 TLS 是低侵入、可回滚的团队部署路径；应用不管理证书，减少密钥管理面。
- 明确把 PG 放到 M5，避免 M4.5 变成“无边界的平台改造”。

## 取舍和影响

- **正向**：M4 范围可控、可本地验证；不改变 ADR-0008 的单写者/数据根安全边界；团队部署有清晰的最小路径。
- **负向**：M4 不支持多实例/HA；并发写能力受 SQLite 限制；登录限速不能跨实例；M4.5 仍不能横向扩展。
- **运维成本**：反向代理配置、代理头信任、Cookie/HTTPS 校验、备份窗口；M5 才需要 PG 运维。
- **兼容**：不新增数据库方言；新增表仍走 SQLite 迁移；M5 时需保持业务表可移植（TEXT/INTEGER、避免 SQLite 专有 SQL）。

## 安全/数据/迁移影响

- TLS 终止在代理时，必须防止伪造 `X-Forwarded-*`：只信任配置的代理地址/网段；应用默认只绑 localhost。
- Cookie `Secure` 依赖 `request.isSecure()`；未正确配置 forwarded headers 时，HTTPS 部署可能下发非 Secure Cookie。S6 验收必须覆盖。
- M4 不改变数据根/实例锁规则；不允许网络盘/云同步根。
- M5 迁移到 PG 需要独立备份/恢复与回滚方案；不得在未演练前切换权威库。

## 验证计划和结果

**S0（本 ADR）**：代码/配置证据核对完成；明确 PG=M5；无代码变更。

**M4 S6（若实施）必须验证**：

1. 反向代理 + 自签证书：`/api/health`、登录、Cookie `Secure`/`HttpOnly`/`SameSite`；
2. 伪造 `X-Forwarded-Proto`/`Host` 不改变安全判定（只信任配置代理）；
3. 默认绑定 localhost；显式局域网绑定 + 防火墙；
4. 备份/恢复演练（含新表）；
5. MCP 只读进程仍可启动、无任务、无写。

**M5 必须验证**：PG 迁移幂等、SQLite/PG 双跑契约、任务并发领取、限速共享、备份恢复、TLS、回滚。

## 回滚或替代路径

- 若团队部署后不需要多实例 → 长期停留在单节点 SQLite；M5 可只做备份/监控/运维加固。
- 若必须多实例 → 按 M5 前置执行；不得以“共享网络盘 + 多写 SQLite”替代（ADR-0008 已拒绝）。
- 若反向代理不可用 → 至少保持 localhost 单机，不暴露明文 HTTP 到局域网。
