# 04 — MVP 策略：完整边界，分阶段交付

## 核心策略

不要做“缩小版产品愿景”，而是做“完整产品中的第一条可工作的纵向链路”。每一阶段实现的都应是未来正式产品的一部分，避免一次性 Demo 架构。

## Phase 0：技术与产品验证（短 Spike）

目标：用真实证据确认 DSH 扩展边界、桌面体验、数据服务和存储的可行性。

Spike：
1. 选定并固定 DSH 版本。
2. 建立最小 out-of-tree Bundle/Plugin。
3. 证明能够注册一个后端服务、一个工具和一个页面/界面入口（按上游当前扩展点）。
4. 证明插件卸载/升级、持久化、测试和日志可用。
5. 记录宿主 API、版本耦合、打包及安全限制。

Spike 的输出是 ADR，不是临时堆代码。

## Phase 1：项目知识底座

包含：组织/用户最小模型、客户、产品、项目、项目资料、工作区关联、项目基线、资料导入、逆向任务记录、知识文档、引用来源、关键词/向量检索、人工审核。

验收：一个项目可以完成资料导入、生成知识、检索回答，并给出可核验引用；换一个无权限用户不能越权检索。

## Phase 2：需求与方案

包含：需求工作项、证据追加、版本化上下文、缺口/冲突识别、需求就绪检查、统一 SolutionModel、业务/技术方案渲染、任务拆分、人工评审和版本记录。

验收：由不完整客户描述开始，补充材料后得到可审核、双视图一致、任务可追溯的方案。

## Phase 3：实施回收与知识闭环

包含：开发交接包、实施记录、Git 差异导入、方案偏差分析、验收矩阵、最终交付快照、知识更新提议与人工发布。

验收：Approved Design 不被覆盖；Actual/As-built 与其差异可追溯；项目知识更新有来源和审核记录。

## Phase 4：企业集成与协同

CSM、Jira、MCP、企业微信、邮件、外部 Agent 适配、多用户协作、共享存储、组织权限细化、服务端任务运行。

**2026-11-13 落地口径**：M4-core 收敛为单节点团队协作 + 只读外部集成 + 站内通知 + 外部 Agent 只读交付；生产 Jira/CSM API、真实邮件/企微启用、PG 多实例、远程 Agent 网关列入 M4.5/M5，见 `docs/specs/M4-PHASE4-PLAN.md`、`docs/specs/M4.5-PHASE45-PLAN.md`。不删除上述能力，只调整交付顺序。**状态：M4 S1–S5 已于 2026-11-13 本机验收；S6 文档化延期；验收见 `docs/M4-ACCEPTANCE.md`。**

## 非功能底线

每个阶段都必须具备：权限边界、错误处理、日志/审计、数据备份思路、自动化测试、文档和迁移策略。不能以“MVP”为理由跳过。

## 延期清单规则

延期能力必须记录在 backlog：名称、用户价值、为什么延期、依赖、恢复条件、目标阶段。不得从产品文档中删除以假装不属于产品。
