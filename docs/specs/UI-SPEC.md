# M1 UI 规格（草案）— 正式产品 UI 基座

- **状态**：Approved & Implemented v0.2（2026-11-12，M1.5 首批已落地；见 §13）
- **日期**：2026-11-12
- **定位**：当前 SPA 作为**正式产品 UI 的基座**演进（路线 A），不是一次性演示壳；技术形态沿用 ADR-0002（独立 SPA + Domain Service 托管）。
- **依据**：`decisions/ADR-0002-TECH-STACK.md`、`docs/00-MASTER-GUIDE.md`、`docs/04-MVP-STRATEGY.md`、`docs/specs/M1-PHASE1-PLAN.md`、`docs/M1-ACCEPTANCE.md`
- **约束**：本规格只定义 UI 结构与交互基线，不改变产品边界、领域规则和 ADR；涉及新框架/状态库/路由库或视觉体系时按需补 ADR。

## 1. 目标与非目标

### 目标
1. 把 M1 的"单页堆叠骨架"重构为**项目上下文优先**的产品壳：全局导航 + 项目内导航 + 页面路由。
2. 让**权限与治理在 UI 上显性可见**（无权限隐藏入口、直接访问给 403 页、不可执行动作给禁用原因），但**以服务端判定为准**。
3. 建立可复用的状态/组件基线（加载、空、错误、冲突、确认、引用展示），避免每个页面各写一套。
4. 覆盖 M1 验收流程中"需要人工浏览器操作"的环节，并开始浏览器 E2E 验证。

### 非目标（本规格不包含）
- 富文本协同编辑、评论、通知中心、移动端专门设计、暗色主题完整化；
- 需求/方案/工作项界面（M2+）；
- 把 UI 嵌入 DSH 客户端 slot（ADR-0002 已定独立 SPA；若未来改变需新 ADR）；
- 视觉品牌最终定稿（本规格只给基线 token 与原则）。

## 2. 设计原则（承接产品原则）

1. **项目上下文优先**：任何资料/知识/检索页面都在明确项目边界内展示，不出现"全局无边界的知识流"。
2. **证据可追溯**：知识文档必须展示来源引用（artifact + locator）；检索结果展示引用数并可追到文档。
3. **人工治理显性**：`draft → needs_review → verified` 状态可视化；"创建者不可自审"等规则在 UI 上给出原因，而不是只报 403。
4. **服务端为准**：UI 只负责减少误操作，不替代权限；所有 401/403/409 都要有可理解的提示。
5. **失败可恢复**：错误信息必须给出下一步（重试、去登录、去补数据），不使用裸错误码。
6. **渐进披露**：复杂表单/管理功能放进独立页面或折叠区，不把所有能力堆在单页。

## 3. 信息架构与路由

```
AppShell（顶栏：产品名｜项目切换器｜当前用户/退出）
  ├─ /login                         登录
  ├─ /setup                         首次引导（仅当系统无任何用户时可用）
  ├─ /projects                      项目列表 / 工作台
  └─ /projects/:projectId           项目上下文（侧栏导航）
       ├─ /artifacts                项目资料
       ├─ /knowledge                知识文档列表
       ├─ /knowledge/:documentId    知识文档详情 / 编辑 / 审核
       ├─ /search                   已验证知识检索
       └─ /members                  成员与角色（owner 可管理）
  ├─ /settings                      账号设置（显示名、改密）
  └─ /403、/404、/error             错误页
```

- 默认落地页：已登录 → `/projects`；`/setup` 只在空库时可达（有用户后访问返回 404 或引导到登录）。
- 路由需要支持刷新直达（后端已托管 SPA；需为未知路径回退 `index.html`，见 §9）。
- 项目切换器保持"当前项目"可见；切换项目时保留在同类页面（如从知识列表切到另一项目知识列表）。

## 5. 状态与权限矩阵

角色：`owner` / `editor` / `reviewer` / `viewer`（服务端 ADR-0006 定义）。UI 表现规则：

| 动作 | owner | editor | reviewer | viewer | UI 表现 |
|---|---|---|---|---|---|
| 查看项目/资料/知识/检索 | ✓ | ✓ | ✓ | ✓ | 始终可见 |
| 上传资料 | ✓ | ✓ | ✗ | ✗ | 无权限时隐藏上传入口 |
| 新建/编辑知识草稿 | ✓ | ✓ | ✗ | ✗ | 无权限时隐藏入口 |
| 提交审核 | ✓ | ✓（创建者或编辑角色） | ✗ | ✗ | 仅 `draft` 显示 |
| 审核通过 | ✓ | ✗ | ✓ | ✗ | 仅 `needs_review` 且**非创建者**显示；创建者看到禁用按钮+原因 |
| 成员管理 | ✓ | ✗ | ✗ | ✗ | 侧栏"成员"入口仅 owner 可见 |
| 修改他人角色 | ✓ | ✗ | ✗ | ✗ | 二次确认（M2 起支持移除） |

> 任何矩阵外的直接访问由服务端返回 401/403；UI 需要把它转换成 P10 错误页，并保留"返回项目"入口。

## 6. 状态与交互规范

- **加载**：首屏 skeleton；局部刷新保持上下文（不整页闪白）。
- **空态**：说明"为什么空 + 下一步 CTA"（例：无资料 → 上传第一份资料；无知识 → 基于资料创建草稿）。
- **错误**：顶部错误条（可关闭、可重试）；表单字段错误内联；403 页面显示"缺少哪个角色/为什么"。
- **冲突**：409（重复编码、重复成员）→ 提示具体冲突对象并聚焦对应字段。
- **会话过期/未登录**：401 → 保存 returnUrl 跳转登录，登录后回跳。
- **CSRF**：变更请求自动带 `X-XSRF-TOKEN`；若 403 且提示 CSRF，自动重新获取一次 token 后重试一次，再失败才报错。
- **审核治理**：创建者视角对"审核通过"显示禁用态与原因"审核人必须是其他项目成员"；`reviewer` 登录后同一位置可点击。
- **破坏性操作**：删除/移除成员在 M2 起提供，统一二次确认并显示影响；M1.5 不提供删除资料（不可变原则）。

## 7. 关键流程（UI 验收路径）

1. **首次使用**：`/setup` 创建管理员 → 登录态 → 创建客户 → 创建项目 → 进入项目资料。
2. **资料入库**：上传 1–3 份资料 → 列表显示哈希/大小，重复内容提示"已存在（去重）"。
3. **知识闭环**：新建草稿（选资料 + 引用位置）→ 提交审核 → 创建者看到"不可自审"提示 → 切换/邀请 reviewer → reviewer 审核通过 → 状态变为已验证。
4. **检索引用**：输入问题 → 命中片段 + 引用数 → 打开文档详情 → 看到来源引用（artifact + locator）。
5. **权限**：viewer 登录 → 上传/新建入口隐藏；直接访问受限 URL → 403 页。

### 本轮修复的真实缺陷

1. **SPA 深链接 401**：安全过滤器先于 SPA 路由拦截 `/projects` 等路径 → 放行 SPA 路由，由前端处理登录跳转。
2. **上传丢文件**：把 `FileList` 交给异步处理后立刻清空 input，导致列表被清空 → 先复制数组再清空；E2E 首次发现该问题。
3. **改密后跳转丢失登录提示**：改密撤销会话使 `logout()` 返回 401，`signOut` 抛出导致跳转被 RequireAuth 重定向覆盖 → 登出改为 best-effort，提示改存会话上下文。
4. **E2E 选择器歧义**：`getByLabel('显示名')` 同时匹配表单 `aria-label="修改显示名"` 与输入框 → 使用 `exact: true`。

- 成员角色变更仅 owner 可操作且无二次确认（移除有确认）；如需审批流在 M2 设计；
