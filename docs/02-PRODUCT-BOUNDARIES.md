# 02 — 产品边界与设计原则

## 1. 产品边界

Mammoth 管理项目上下文和工作过程；外部业务系统继续管理它们各自的权威业务交易。Mammoth 可以通过导入、API 或 MCP 获取外部资料，但不应把外部系统的记录私自复制后当作权威数据。

## 2. 主数据关系

- 一个客户可关联多个项目。
- 一个产品可应用于多个客户和项目。
- 一个项目可关联一个或多个产品，具体按项目范围建模。
- 产品标准知识、客户业务知识、项目实际知识必须有不同 scope。
- 工作项必须归属一个主项目；跨项目事项用明确的关联关系表达，不能靠复制记录。

“客户 + 产品 = 项目”仅作为常见的创建向导默认路径，不应成为唯一的数据约束。

## 3. 知识边界

- 产品知识：标准产品能力、标准业务流程、标准数据模型、版本演进。
- 客户知识：客户组织、业务背景、合同约定、管理制度、沟通履历。
- 项目知识：实际部署版本、源码、数据库、定制逻辑、项目决策、实施记录。
- 通用经验：跨客户可复用的模式和经验；必须去除客户专属信息并经授权审查。

不得将某客户的项目事实自动提升为产品标准知识或公司通用经验。

## 4. 工作项边界

第一版优先实现需求工作项，但领域模型预留缺陷、问题、优化、技术债、交付事项等类型。类型可以采用不同模板与状态流，不得将不同流程硬塞进单一需求状态机。

## 5. 人机职责

Agent 可以：归纳、检索、比较、提出问题、给出方案候选、拆分任务、生成文档、分析代码差异。

人必须决定：客户意图、范围取舍、业务规则、方案审批、生产数据操作、最终交付和知识升级为正式事实。

## 6. 防止产品范围被 Vibe Coding 蚕食

每次要求“先简单一点”时，Agent 必须把改动归类为：
- 实现延期：功能仍在路线图中；
- 技术替代：能力不变，换一种实现；
- 需求裁剪：产品能力被删除，需用户批准；
- 风险豁免：降低质量或安全要求，原则上拒绝。

不得把“这次先不做”悄悄改写为“产品不需要”。所有延期能力必须进入 backlog，标注原因和计划阶段。
