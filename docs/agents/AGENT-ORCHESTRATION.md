# Agent Orchestration — Lead 与 SubAgent 协作规范

**版本：** 0.2  
**适用范围：** 使用 DeepSeek Harness 对 Mammoth 进行 Vibe Coding。

## 1. 基本原则

Lead Agent 是唯一任务总协调者。SubAgent 是被委派的有限任务执行者，不是平级产品决策者。

- Lead 对任务理解、范围、授权和最终结果负责。
- SubAgent 对其被委派的调查/设计/实现/评审报告负责。
- SubAgent 不得擅自改变产品边界、已批准规格或 ADR。
- 子 Agent 的输出是建议或工作结果，不能直接视为已批准决策。
- 不以 SubAgent 数量衡量工作质量；能由一个 Agent 清楚完成的任务不要强行拆分。

## 2. 何时应该委派

适合委派：

- 需要独立观点的技术/架构评审；
- 多个相互独立的仓库调查；
- 官方文档/依赖版本调研；
- 可并行的测试设计；
- 针对一个明确 Commit/diff 的独立审查；
- 不同且边界清晰的模块只读勘察。

不适合委派：

- 用户目标和关键业务规则仍不清楚；
- 任务上下文很小，委派通信成本高于收益；
- 多个子任务需要频繁共享未完成的推理；
- 多个 Agent 必须同时修改同一文件/同一模块；
- 数据库迁移、领域模型或架构决策尚未批准；
- 没有办法隔离并行写入。

## 3. 角色选择建议

| 任务意图 | 优先角色 | 是否通常并行 |
|---|---|---|
| 把模糊需求写成规格 | Product Analyst | 可与只读技术调查并行，但事实需汇总 |
| 查现有实现/官方文档 | Research Analyst | 适合并行 |
| 评价架构方案 | Architecture Reviewer | 可与 Research 并行，只读 |
| 实现已批准任务 | Implementation Agent | 按任务拆分；写入需隔离 |
| 设计测试 | Test Designer | 可与实现前的准备并行 |
| 审查实现结果 | Independent Reviewer | 实现完成后独立执行 |

## 4. 委派前必须生成自包含任务包

Fresh/Spawn 子 Agent 通常没有主会话的完整对话上下文。不要只发送一句“分析一下”。至少包括：

```text
角色定义：docs/agents/<ROLE>.md（请先读取并遵守）
任务目标：一句话可验证目标
背景：必要业务背景，不引用“上面说过”
项目：仓库路径、模块、分支/Commit
输入：具体文件、Spec、Task、日志、diff
问题：必须回答的问题清单
写入权限：只读 / 允许写入的精确路径
禁止事项：不可执行命令、不可访问资源、不可修改范围
输出：必须遵守该角色文件的报告格式
完成定义：何种证据才算完成
```

任务包必须足够自包含。对大文件给路径和相关范围，不要不加选择地复制全部仓库上下文。

## 5. Fresh、Fork 与外部执行的选择

### Fresh / Spawn（默认优先）

适用于独立调查、第二意见、测试设计、独立评审。子 Agent 从新上下文开始，因此必须提供完整任务背景。它有自己的 Agent 会话，但不代表拥有独立 Git 工作区。

### Fork

只有当子任务需要主会话已经完成的对话上下文时才使用。Fork 通常继承父会话已完成轮次，但不应假设它继承父 Agent 的全部授权、工具能力、运行状态或当前尚未完成的工具调用。需要验证该 DSH 版本的具体行为。

### 外部执行 Agent

当当前 Profile 实际暴露并配置了 Codex/Claude 等外部委派工具时，可以用于独立执行任务。外部执行可能是单次任务式调用，是否可继续对话取决于所选 Provider。委派前应确认凭据、目录、网络、成本和安全范围。

## 6. 并行写入与 Worktree 规则

最重要的规则：**SubAgent 会话隔离不等于文件系统隔离。**

- 多个只读调查可以在同一 Workspace 并行。
- 多个编码 Agent 不得默认在同一 checkout 修改代码。
- 并行编码必须为每项任务分配独立 Git Worktree/分支，并明确写入范围。
- 不能为某任务建立独立 Worktree 时，编码任务串行执行。
- 同一个数据库迁移、共享 DTO、公共契约和根配置文件原则上只允许一个写入者。
- AgentTeam 的任务板文件路径提示通常只是冲突警告，不是文件锁或权限控制。
- AgentTeam 成员共享同一 checkout；不要把它误当成自动隔离工作区。

## 7. AgentTeam 的使用条件

仅当以下条件大部分成立时启用：

- 至少 3 个明确独立的子任务；
- 任务之间有依赖关系或共享进度需要；
- Lead 需要统一查看任务 owner、状态和依赖；
- 每个子任务的输出和修改范围可以清楚定义。

仅需一个 Reviewer 或一个 Research 子 Agent 时，普通 SubAgent 更合适。

AgentTeam 是会话级能力。根据当前官方文档，新 Session 默认 Team mode 关闭，需要在根 Session 的模型/推理设置中启用；不同 DSH 版本和 Profile 可能不同，必须在当前 UI/工具目录核实。

## 8. Lead 的执行流程

1. 先独立理解用户目标、读取 `AGENTS.md` 和相关规格。
2. 判断当前任务是否真的值得委派。
3. 选择一个或多个角色，读取对应角色文件。
4. 为每个子 Agent 生成自包含任务包。
5. 只读任务可以并行；写任务先确定 Worktree/写入范围。
6. 收集报告，检查证据、假设、冲突和遗漏。
7. 对冲突结论进行复核；必要时再委派独立研究，不让子 Agent 自行投票决定。
8. Lead 形成唯一的综合建议或实施计划。
9. 涉及产品、架构、安全、数据迁移和范围的决策交给负责人确认。
10. 完成后将有价值的结论更新到正式规格、ADR、任务卡或知识文档。

## 9. 失败与冲突处理

- 子 Agent 失败/超时：保留任务记录，判断是否缩小范围或改为主 Agent 执行；不要重复启动造成成本堆叠。
- 输出缺乏证据：要求补充路径、行号、命令和版本；无法补充则标记为未验证。
- 结论冲突：回到原始代码/官方资料/测试证据；不以多数票决策。
- 范围越权：停止使用其未授权改动，审查 diff，必要时回滚必须由人批准。
- 共享文件冲突：暂停相关写任务，确定唯一 owner，再串行合并。

## 10. 上下文与成本控制

- 角色文件只承载稳定职责；每次任务包只传当前任务必要资料。
- 不把整个项目所有文档复制给每个子 Agent。
- 对独立审查优先使用 Fresh，降低主会话结论锚定。
- 对必须继承详细讨论的后续分析才考虑 Fork。
- 简单任务不要创建 SubAgent。
- Lead 必须汇总去重，不能将多个冗长报告不加整理地原样拼接。

## 11. 标准委派记录

每次重要委派建议在工作项日志记录：

- Agent 名称/角色；
- Fresh/Fork/External；
- 任务目标与输入版本；
- 写入权限/Worktree；
- 输出位置；
- 结果状态；
- Lead 是否采纳及理由。
