# 10 — Vibe Coding 工程方法手册

## 1. 我们采用什么 Vibe Coding

不是“自然语言描述一次，然后让 Agent 自由发挥直到项目完成”。我们采用 Spec-guided、Plan-first、Test-backed、Human-governed 的迭代式 Vibe Coding。

人负责目标、边界、取舍和验收；Agent 负责探索、方案草拟、实现、测试辅助和文档整理；Git 和自动化测试负责可追溯与可验证。

## 2. 最小工作单元

一个任务应足够小，能在一个明确的上下文中完成并验证。典型目标是一个端到端行为或一个领域能力，不是“把整个项目管理模块做完”。任务通常包含：用户价值、场景、非目标、验收条件、依赖、风险、测试。

## 3. 六步工作循环

### A. Discover

让 Agent 阅读 Master Guide、相关规格、架构、当前代码、测试和 Git 状态。先回答“现在有什么”，不能直接假设。

### B. Specify

先写需求/任务规格。把模糊自然语言转成用户场景、业务规则、状态变化、边界、验收条件。存在高影响未知时先问，不要补脑。

### C. Plan

计划应包含：拟修改文件/模块、数据变化、API/UI变化、测试路径、回滚与风险。计划阶段不应提前修改代码。

### D. Implement

按步骤实现。优先完整纵向切片。先建立失败测试或可检查验收点，再实现。避免一次大量重构与新功能混在同一个变更里。

### E. Verify & Review

真实运行检查；查看完整 diff；检查权限、数据、异常、兼容性和文档。Agent 不能引用未运行的测试为“通过”。

### F. Record & Handoff

更新任务状态、ADR、工作日志；超出会话上下文时写交接文档。新会话必须先读取交接资料，不依赖旧聊天记忆。

## 4. 多会话策略

- 一个主会话维护产品方向和当前里程碑，不直接承担所有实现细节。
- 需求/架构会话负责规格和决策，不与实现会话同时编辑同一文档。
- 实现会话一次聚焦一个任务或一个独立工作树。
- Review 会话只审阅指定 Commit/diff 和规格，不在未授权时顺手修改代码。
- 研究会话只负责提供证据和建议，产出必须回写到正式文档或 ADR。

## 5. SubAgent 使用原则

角色定义见 `docs/agents/`。它们是 Lead Agent 委派时读取的 Role Prompt，不会自动在 DSH 注册成永久 Agent。

适合并行：独立代码勘察、官方文档研究、测试设计、依赖/安全研究、不同模块只读审查、独立 diff Review。

不适合并行：多个 Agent 同时改同一文件/模块；需求边界尚未明确；共同修改数据库迁移；多个 Agent 对同一架构作出互相冲突的实现；任务高度依赖连续共享上下文。

主 Agent 必须定义每个子任务的输入、输出、文件范围、是否只读、禁止事项、验收标准，并整合结果。Fresh 子 Agent 必须收到自包含上下文。Fork 只用于需要继承已完成对话上下文的情况，不代表继承全部权限。

**并行编码必须采用独立 Git Worktree/分支。** SubAgent 是会话/上下文边界，不保证文件系统隔离。AgentTeam 只提供共享任务板与任务协调，官方文档指出队友共享同一个 checkout，任务板的文件重叠提示不是锁或写权限控制。不能真正隔离时，编码任务串行执行。

AgentTeam 是可选协调工具，不是默认复杂度。启用前核对当前 Session 是否开启 Team mode，以及当前 Profile 是否实际提供任务板工具。

## 6. Git 与并行开发

- 主分支保持可构建。
- 每个功能/缺陷使用短生命周期分支或 Git Worktree。
- 每个任务先检查 `git status` 和当前分支。
- 禁止丢弃用户改动；禁止无理由重写历史；禁止裸 `--force`。
- 不同 Worktree 必须有独立任务范围；合并前先运行测试和 Review。
- Commit 要说明目的，不以“AI generated”代替内容描述。

## 7. 上下文工程

每个新会话先给：Master Guide、相关产品规格、相关 ADR、任务卡、当前 Git 状态、最近工作日志。不要把所有文档一次性塞进上下文。

当上下文接近上限或任务需要换会话：
1. 生成 SESSION-HANDOFF；
2. 写明已经确认的事实、未确认假设、改动文件、测试结果、未完成项；
3. 提交/保存可恢复的代码状态；
4. 新会话先读交接文档和仓库，而不是直接续写旧聊天。

## 8. 让 AI 教会你，而不只是替你写

每个技术任务结束时要求 Agent 用简短说明回答：
- 这次采用了什么架构/设计模式？
- 为什么选择它？
- 有哪些替代方案？
- 关键代码/数据流在哪里？
- 哪些测试证明其正确？
- 作为项目负责人，我应理解哪三个关键点？

## 9. 控制“AI 自行扩大范围”

任务进行中发现额外问题时，Agent 先记录为 follow-up，不在当前任务顺便重构。若确实阻塞任务，说明依赖和最小必要修改并请示。

## 10. 失败恢复

若构建/测试失败：区分原有失败与本次引入；保留错误证据；先定位再修复；不得通过删除测试、放宽类型、吞异常或硬编码假数据来制造绿色结果。

## 11. 适合本项目的节奏

每个里程碑：产品规格 → 架构验证 → 任务拆分 → 小步实现 → Review → 用户验收 → 复盘。
每个功能：尽量 0.5–2 天内可独立验收；若明显更大，继续拆分。此为任务粒度建议，不是对工期的承诺。
