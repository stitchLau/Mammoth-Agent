# 07 — 工作项与需求生命周期

## 1. 通用工作项模型

所有工作项共享：编号、项目、类型、标题、描述、提出来源、负责人、参与人、优先级、状态、标签、证据、讨论、决策、关联工作项、活动时间线、附件和审计记录。

类型特定字段与工作流通过模板扩展，不把所有工作项限定为需求。

## 2. 第一版需求流程

`draft → collecting → ready_for_analysis → analyzing → solution_review → approved → in_development → pending_acceptance → pending_knowledge_sync → closed`

需要支持：`blocked`、`on_hold`、`withdrawn`、`rejected`。

## 3. 需求收集

允许多批次追加文字、文档、图片、转录文本、会议纪要、邮件内容和其他附件。原始证据不可被 AI 改写覆盖。

每次新增证据后，Agent 应输出：
- 本次新增事实；
- 与已有内容一致的部分；
- 新增/修正/冲突/疑似重复；
- 仍然未知的信息；
- 建议向客户/业务方确认的问题；
- 对需求范围和验收条件的影响。

## 3A. 外部系统证据（M4，2026-11-13）

- Jira/CSM 导入先落 `external_record`（外部 ID/版本/哈希/来源 URL）与“证据候选”，**不直接改工作项状态**。
- 人工映射后才生成 `requirement_evidence`（`evidence_type=jira/external`），`artifact_id` 指原始导入文件，`locator` 指外部 key/URL；证据仍只追加、不可覆盖。
- 外部版本变化生成新记录/新证据批次，不覆盖旧证据；重复导入幂等。
- 外部状态/优先级只是来源信息，不自动成为 Mammoth 的需求状态/优先级结论。

## 4. Ready for Analysis 的判断

Agent 根据需求类型和复杂度模板判断是否存在关键缺口。至少检查：背景、目标、当前流程、期望流程、业务规则、涉及角色/范围、异常场景、数据口径、外部依赖、验收方式、实施限制。

Agent 只能给出建议；需求负责人确认是否进入方案阶段。缺少非关键细节时允许带假设进入，但必须显式标记并设置决策责任人。

## 5. 方案生成

先形成结构化统一 SolutionModel，再生成：
- Business Solution：现状、目标、角色、业务流程、规则、异常处理、现场执行、管理影响、验收；
- Technical Solution：代码/模块影响、数据设计、接口、权限、兼容性、异常处理、性能、安全、测试与部署；
- Task Breakdown：任务、依赖、负责人建议、完成条件；
- Traceability Matrix：业务目标 → 流程/功能 → 技术项 → 任务 → 验收。

## 6. 方案评审

方案审查至少覆盖：客户既定目标、业务闭环、管理成本、现场可执行性、技术可行性、数据正确性、兼容性、权限、安全、回滚/迁移、测试与验收。

方案版本必须保留：作者、输入基线、变更摘要、评审意见、批准人、批准时间。批准版本不可静默覆盖。

## 7. 开发交接

输出可携带的交接包，包含 approved business/technical solution、开发任务、项目技术约束、相关代码映射、数据关系、验收与测试要求。外部 Agent 不应得到生产凭据。

## 8. 结项

收集实际 Commit、修改文件、迁移/DDL、测试结果、现场确认、偏差和未完成事项。Agent 对照 Approved Design 识别：符合、偏离、额外实现、未实现、客户变更、技术替代、缺陷修复。

经人工确认后生成 As-built / Final Delivery，更新知识文档；保留原始方案和实施记录。
